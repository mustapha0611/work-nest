# ADR 0007: Database-backed opaque session tokens

- Status: Accepted
- Date: 2026-11-02

## Context

M4 adds sign-in to an API that until now had no notion of a caller. Every protected request after this
point needs an answer to "who is this?", and the answer has to be revocable: an account can be
deactivated ([ADR 0006](0006-user-deactivation.md)), a password can be changed, and a laptop can be
lost.

The browser is the only client. That matters because a browser will happily attach credentials to
requests initiated by any site unless the credential is constrained — which is the CSRF problem.

Three broad designs were on the table:

- **Stateless tokens (JWT).** The server signs a payload and trusts it later without a lookup.
- **Opaque tokens in the database.** A random secret identifies a row; the row is the session.
- **Signed cookies with no database row.** The cookie itself carries the session state, protected by a
  server key.

## Decision

### The token

- A session token is 32 bytes from `crypto.randomBytes`, encoded as base64url (43 characters). It is a
  credential, not an identifier: it exists to be unpredictable, so it is generated by the one API whose
  job is randomness.
- `Session.id` remains a UUID v7, like every other primary key. A UUID v7 is _not_ used as the token:
  it embeds a creation timestamp, the version leaves the random portion smaller than 256 bits, and
  identifiers get logged and displayed in places a credential must never appear.

### Storage

- The database stores only `SHA-256(token)` in `Session.tokenHash`, which is unique and indexed.
- SHA-256, not argon2. A password is low-entropy and guessable, so hashing it must be slow. A session
  token is 256 bits of uniform randomness with no dictionary to attack, so a fast hash is enough. Using
  argon2 here would add its cost to **every authenticated request** and change nothing an attacker can
  exploit.
- The plaintext token exists only in the cookie and in the response that sets it. It is never logged,
  never returned in a JSON body, and cannot be recovered from the database.

### Lifetime and revocation

- `Session.expiresAt` is an absolute timestamp, seven days by default (`SESSION_TTL_DAYS`). The cookie
  carries the matching `Max-Age`.
- There is **no sliding renewal** in M4. A session dies at a fixed moment whether or not it was used.
  Sliding expiry is a usability decision that also extends the life of a stolen cookie; if it is added,
  it should come with a maximum absolute lifetime as well.
- The database row is the only clock the server trusts. A client can edit or delete its own cookie;
  it cannot edit `expiresAt`.
- Revocation is a `DELETE` on the row. Sign-out is therefore immediate and does not require a denylist
  or key rotation.

### The cookie

| Attribute  | Value                                 | Why                                                                     |
| ---------- | ------------------------------------- | ----------------------------------------------------------------------- |
| `HttpOnly` | always                                | JavaScript cannot read the token, so XSS cannot exfiltrate it directly. |
| `SameSite` | `Lax`                                 | Blocks cross-site POSTs; this is the CSRF defence.                      |
| `Secure`   | only when `NODE_ENV === 'production'` | Local development runs over plain HTTP, where a browser drops it.       |
| `Path`     | `/`                                   | One API origin serves every route.                                      |
| `Max-Age`  | `SESSION_TTL_DAYS` in seconds         | The cookie should not outlive the row behind it.                        |

`POST /api/auth/logout` is public and idempotent. It returns `204` even when there is no session. A
protected logout would return `401` to a client whose session had already expired, leaving that client
unable to clear its dead cookie without special-case handling.

### CSRF

No separate CSRF token is issued in M4. The API is same-origin with the Angular app (a dev proxy today,
one origin in production), and `SameSite=Lax` means a cross-site form post or `fetch` does not carry the
session cookie. This is a deliberate assumption with a named failure condition: **if the API is ever
served cross-origin from the app, this decision must be revisited before the change ships.**

### Rate limiting

Sign-in has two in-memory limits per 15-minute window:

- per address + email (5 attempts): one account cannot be brute-forced.
- per address (20 attempts): one host cannot spray many accounts from a leaked password list.

IPv6 addresses are grouped with `ipKeyGenerator`, because a /64 gives an attacker effectively unlimited
"different" addresses. The store is per process: with N API instances the effective limit is N times the
configured value. A shared store (Redis) is the fix, and it becomes necessary when the API runs more
than one instance — not before.

`TRUST_PROXY` must stay off until there is a real proxy in front of the API. Without it, `req.ip` is the
proxy's address and every user shares one bucket; with it enabled and no trusted proxy, a client can
spoof `X-Forwarded-For` and mint fresh keys. The setting is coupled to deployment, so it is left out of
M4.

## Alternatives considered

- **JWT access tokens.** Verification is cheap and stateless, but revocation requires a denylist that
  reintroduces the database lookup the token was meant to avoid, and the payload goes stale as soon as
  a user's role or account state changes. The stateless benefit only pays off across many services,
  which this project does not have.
- **Signed cookie with no session row.** Same revocation problem, plus a signing key that must be
  rotated without logging everyone out. It also makes "sign out everywhere" impossible.
- **Argon2 for the token hash.** Adds deliberate slowness to the hottest path in the API (every
  authenticated request) to protect a secret that has no dictionary. The wrong tool for a
  high-entropy value.
- **Bearer token in `localStorage`.** Readable by any script on the page, so a single XSS becomes
  account theft, and the client has to attach it to every request manually. `HttpOnly` cookies are
  strictly better for a browser-only client.
- **UUID v7 as the token.** Leaks creation time, leaves less randomness than 32 random bytes, and puts
  a credential where identifiers are normally handled.
- **Sliding expiry now.** Convenient, but it extends the window for a stolen cookie and adds a write to
  the session row on every request. Deferred until there is evidence users need it.

## Consequences

- Every authenticated request performs one indexed lookup on `Session.tokenHash`. This is the price of
  immediate revocation and it is paid on the hot path; the unique index is what keeps it cheap.
- Expired session rows accumulate. M4 accepts that: rows are small, and a periodic cleanup job (or a
  filtered delete when the table grows) is a Later concern, not a schema change.
- Signing out everywhere is a single `DELETE WHERE userId = ...`, which is also what deactivation will
  use when that admin flow is implemented.
- A stolen cookie is live until it expires. Seven days is the blast radius; the session row can be
  deleted as soon as the theft is noticed.
- Multi-instance deployments need a shared rate-limit store, while sessions themselves already work
  across instances because they live in PostgreSQL.
- The same-origin assumption is load-bearing. Moving the API to a separate origin requires a CSRF
  token, not just a CORS change.
